# PHASE 2 — OPENAI VLM SCENE ANALYSIS

## Goal

When the user clicks **"Analyze Scene"**, IrisMap must analyze the currently visible remote-sensing/map scene.

### Frontend behavior

When "Analyze Scene" is clicked:

1. Capture the currently active map viewport/canvas.
2. Convert the visible map/canvas to a base64 image.
3. Capture:
   - latitude
   - longitude
   - zoom level
   - selected imagery band
   - selected composite mode
   - active map provider/layer
   - viewport dimensions if available
4. Send this information to:

`POST /api/analyze-scene`

Do not send unnecessary image data or application secrets to the browser.

### Backend endpoint

Implement:

`POST /api/analyze-scene`

Use the OpenAI Node SDK.

Read the API key ONLY from:

`process.env.OPENAI_API_KEY`

Never hardcode the API key.

Preferred model:

`gpt-4o`

If the existing project requires a cheaper/faster model, allow:

`gpt-4o-mini`

Make the model configurable through an environment variable if appropriate.

### Request structure

Use a structured request similar to:

```json
{
  "image": "data:image/png;base64,...",
  "center": {
    "lat": 17.XXXX,
    "lng": 78.XXXX
  },
  "zoom": 12,
  "band": "thermal",
  "composite": "false-color",
  "mapProvider": "esri"
}
```

Adapt the exact structure to the existing application architecture.

### Remote-sensing system prompt

Create a specialized remote-sensing analysis prompt.

The model must understand that:

- the image may be satellite/remote-sensing imagery
- the selected band/composite affects interpretation
- visual conclusions are estimates, not ground-truth measurements
- the model must not invent objects that cannot reasonably be inferred from the image

Ask the model to analyze:

- terrain classification
- estimated urban density
- visible roads/infrastructure
- water bodies
- vegetation indicators
- thermal anomalies when thermal imagery is selected
- unusual or potentially significant regions
- confidence level
- detected tags

### Structured response

Force the model to return machine-readable JSON.

Use a schema similar to:

```json
{
  "summary": "string",
  "terrainClassification": {
    "type": "string",
    "confidence": 0
  },
  "urbanDensity": {
    "classification": "low | medium | high",
    "confidence": 0
  },
  "infrastructure": [
    {
      "type": "road | building | bridge | industrial | other",
      "description": "string",
      "confidence": 0
    }
  ],
  "waterBodies": [
    {
      "type": "river | lake | reservoir | pond | other",
      "description": "string",
      "confidence": 0
    }
  ],
  "vegetation": {
    "classification": "string",
    "confidence": 0
  },
  "thermalAnomalies": [
    {
      "description": "string",
      "severity": "low | medium | high",
      "confidence": 0
    }
  ],
  "detectedTags": [],
  "limitations": []
}
```

Adapt the schema if necessary, but maintain predictable JSON.

Validate the response before returning it to the frontend.

If the model returns invalid JSON:

1. Attempt safe parsing/recovery.
2. If recovery fails, return a controlled API error.
3. Never crash the server.

### Frontend presentation

Display results in the existing **AI Scene Analysis** panel or create a clean overlay/modal integrated into the existing UI.

Show:

- AI summary
- terrain classification
- urban density
- infrastructure
- water bodies
- vegetation
- thermal anomalies
- confidence scores
- detected tags
- analysis metadata:
  - coordinates
  - zoom
  - selected band
  - composite
  - map provider

Add:

- loading state
- progress/analysis state
- success state
- error state
- retry button

Never leave the user with a blank screen if analysis fails.
